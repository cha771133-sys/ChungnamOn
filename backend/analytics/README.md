# B10 · KPI 이벤트 및 관리자 조회

이벤트 저장 → 기존 업무 모델 연동 → 6개 KPI 집계 → Django Admin 조회 → 회귀 테스트 순으로 구현했다.
현재 업무 로직의 더미·미구현 상태를 지표에서도 그대로 드러내는 최소 운영 화면이다.
Railway 설정·환경변수·서비스·운영 DB·배포를 변경하거나 조회하지 않는다.

## 사용

로컬·테스트 DB에서만 `python manage.py migrate`를 실행한다. 새 환경변수·외부 서비스는 필요하지 않다.
`analytics.view_kpievent` 권한을 가진 활성 staff 또는 superuser가 다음 화면을 조회한다.

- `/admin/analytics/kpievent/`: 이벤트 종류·기간·언어·데이터 구분 필터, 업무 ID 검색, 50건 페이지, 최신순
- `/admin/analytics/kpievent/summary/`: 최근 7일·30일, 전체 또는 실제 지원 언어/언어 미확인

일반 사용자·미인증 접근은 기존 Admin 인증으로 차단하고, staff도 모델 조회 권한이 없으면 403이다.
추가·수정·삭제·일괄 작업은 제공하지 않는다. 문서 이름·파일·원문·질문·답변·사용자 프로필을 표시하지 않는다.
집계 조회는 DB를 수정하지 않는다. 사용자 지정 기간과 새 설문 모델/API는 구현하지 않았다.

## 단일 집계 기준과 한계

| KPI | 기준 | 현재 상태 |
| --- | --- | --- |
| 문서 해석 완료율 | 최초 REAL 분석 시작이 기간 안에 있는 문서 중 종료 전 완료 이벤트와 현재 번역·요약 결과가 함께 있는 문서 | 서버 처리만 부분 측정. 현재 파이프라인은 더미이므로 운영 분모 없음 |
| 교차 검증 일치율 | 항목별 실제 대조 시도·최종 상태 필요 | `NOT_MEASURABLE`: 항목 모델·시도 계약 없음 |
| 체크리스트 완료율 | 문서별 유효 체크리스트·항목 현재 상태 필요 | `NOT_MEASURABLE`: Checklist/ChecklistItem 없음 |
| 마감일 등록률 | 확인된 기한의 문서와 실제 연결 Schedule 필요 | `NOT_MEASURABLE`: 확인 계약·Schedule 없음 |
| 챗봇 근거 답변 비율 | REAL 저장 이벤트와 실제 생성 답변 모델의 연결. 분자는 저장 시 공식 근거가 검증된 GROUNDED 답변 | 현재 어댑터는 더미이므로 운영 분모 없음 |
| 내용 이해도·실제 도움 만족도 | 기존 실제 응답과 확정된 점수 척도 필요 | `NOT_MEASURABLE`: 수집 기능 없음. 기획·프론트 계약 후 후속 작업 |

계산 가능한 지표의 분모가 0이면 `NO_DATA`, 비율은 `None`/N/A이다. 측정 불가 지표의 분자·분모는
알 수 없으므로 `None`/대시로 표시한다. 기본 점수·목표치·가상 응답 수를 만들지 않는다.
언어는 `UserProfile.Language`의 실제 지원 코드(vi, en, zh, uz, ne, th, ko)만 허용한다.
국적·체류자격으로 언어를 추정하지 않는다. 언어별 소규모 집계도 동일한 Admin 모델 권한으로 제한한다.

문서 집계는 최초 실측 시작 당시의 언어를 기준으로 하며 재시도는 분모를 늘리지 않는다.
실패·OCR 실패도 시작 이력이 있으면 분모에 포함한다. 서버 완료와 결과 API 200 응답 생성은 별도 지표다.
현재 번역·요약 존재도 확인하므로 과거 상태를 완전히 재현하는 시계열 지표는 아니다.
성공한 API 응답은 브라우저 수신·렌더링의 증거가 아니다. **화면 표시율은 측정 불가**다.

기간은 timezone-aware 종료 시각에서 7일/30일을 뺀 시각 이상, 종료 시각 미만이다.
완료·실패·제공은 같은 문서 집합의 최초 실측 시작 이후, 종료 전 이력만 본다.
과거에 시작한 문서의 이번 기간 재시도를 새 문서로 세지 않는다.
실패 후 성공한 문서는 실패 이력과 완료 양쪽에 표시될 수 있다.

챗봇은 질문/요청 수가 아닌 실제 저장 답변 ID를 중복 없이 센다. 공식자료의 실제 ID, 승인·사용 상태,
재처리 필요 여부, 공식 URL 허용 목록, 본문 해시와 확인일 스냅샷 일치를 검증한다.
URL 문자열만 있거나 없는 출처 ID·변경된 스냅샷이면 GROUNDED로 수집하지 않는다.
근거는 **저장 당시**의 검증 사실이며 출처가 나중에 변경되어도 과거 답변 전체 정확성을 보증하지 않는다.
답변 보류와 AI 호출 장애를 구분하는 영속 계약은 없어 두 건수는 `NOT_MEASURABLE`이다.
실패 요청은 답변/성공 이벤트를 만들지 않는다. 검증 일치율과 챗봇 근거 비율을 AI 정확도·행정적 정답률로 표현하지 않는다.

## 이벤트 계약

`analytics.services.event_service.record_event`는 신뢰하는 서버 코드 전용이다. 공개 수집 API는 없다.
이벤트 종류, 업무 종류, 양의 정수 ID, 실제 언어 코드, timezone-aware 발생 시각을 검증한다.
`properties`는 아래 정확한 속성 집합만 허용한다. 키 추가·누락·임의 문자열·숫자 대신 boolean 사용을 거부한다.

| 이벤트 | 허용 속성 |
| --- | --- |
| DOCUMENT_ANALYSIS_STARTED | 없음 |
| DOCUMENT_INTERPRETATION_COMPLETED | has_translation, has_summary: boolean |
| DOCUMENT_INTERPRETATION_FAILED | stage: 기존 단계 코드 |
| DOCUMENT_RESULT_PROVIDED | 없음 |
| CHAT_ANSWER_CREATED | status: GROUNDED/UNVERIFIED/MISMATCH, grounded: boolean, official_source_count: 0~20 정수 |

챗봇 이벤트는 실제 저장 답변과 공식자료에서 재계산한 속성이 일치해야 한다.
원문·OCR·해석 전문·질문·답변·인증정보·IP·User-Agent·민감 요청 본문·임의 오류 문자열을 받거나 저장하지 않는다.
사용자 FK/국적/체류자격도 저장하지 않는다. 업무 전이 식별자 원문은 저장하지 않고 SHA-256 키로 중복을 막는다.
문서 시작은 관찰된 OCR 진입마다 서버 시도 ID가 다르며, 완료·실패는 해당 시작 이벤트 ID에 연결된다.
같은 OCR 상태의 반복 저장은 시작을 늘리지 않는다. 답변 생성은 재시도 키와 무관하게 답변 ID당 하나다.
중복 키에 다른 사실을 쓰려 하면 거부한다. 발생 시각과 실제 저장 시각은 별도 필드다.

## 기존 업무 연동과 수집 누락

A 담당 `documents` 파일·모델·핵심 서비스는 수정하지 않았다. analytics의 저장 신호는 실제 저장된
OCR 진입·DONE·FAILED 전이를 관찰하고, middleware는 기존 `document-result` GET의 성공 응답만 관찰한다.
단순 업로드·상태 조회·409/404/401은 결과 제공으로 기록하지 않는다. 현재 문서 구현에는 더미 AI 함수만 있으므로
관찰 이력은 항상 `DUMMY`다. 분석 시작 단계의 실제 언어가 확인되지 않으면 빈 값으로 보존한다.

B 담당 `chatbot`은 기존 답변 저장 트랜잭션 안에 최소 호출 한 곳을 추가했다.
`CHATBOT_AI_MODE=dummy`는 `DUMMY`, 현재 계약이 없는 다른 모드는 `UNKNOWN`이다.
지원하지 않는 모드를 실제 업무로 추측하지 않는다. 실제 AI 전환 때 **시도 ID·데이터 출처·언어 스냅샷 계약을
먼저 합의하고 기존 관찰자를 교체**해야 한다. 현재 자동 연동이 `REAL` 이벤트를 만들지는 않는다.
테스트는 테스트 DB에서만 REAL 분류를 사용해 집계 규칙을 검증한다.

`record_event`는 오류를 전달하므로 호출자가 업무와 원자적으로 저장할 수 있다.
현재 관찰 경로는 내부 savepoint에서 실패를 격리하고 `KPI_EVENT_NOT_RECORDED` 고정 경고만 남긴다.
질문·문서가 섞일 수 있는 예외 원문이나 입력은 로그에 출력하지 않는다.
챗봇 및 기존 문서 결과 저장의 외부 트랜잭션이 롤백되면 성공한 이벤트도 롤백된다.
일부 문서 전이는 기존 서비스가 autocommit으로 저장하므로 완전한 원자적 이벤트 수집을 보장하지 않는다.
저장 실패를 복구한 것으로 위장하거나 `on_commit`의 유실을 숨기지 않는다.

`QuerySet.update`, `bulk_create`, 직접 SQL 및 B10 도입 전 이력에는 관찰 신호가 없다.
일반 `save`도 업무 상태를 변경하지 않은 저장은 이벤트를 만들지 않는다. 누락된 시작을 추측해서 만들지 않는다.
관리자 화면은 기간 내 생성 문서 중 시작 누락, 생성 답변 중 이력 누락, 데이터 구분별 이벤트 건수를 별도로 제공한다.
이 진단은 선택 언어와 무관한 전체 기간의 현재 모델 기준이며, 원인/모든 과거 누락을 확정하지 않는다.
집계 기준이 다른 진단 건수를 KPI 분모에 더하지 않는다. 최초 저장 시각을 표시하고 과거 이벤트를 역생성하지 않는다.
보존되지 않은 이력이 있으므로 이벤트 수집이 완전하다고 주장하지 않는다.

## 보관·삭제

`KPI_EVENT_RETENTION_DAYS=None`은 보관 정책 미확정이다. 정책값은 설정에서 분리하고 화면에 표시한다.
자동 삭제 명령·스케줄러·실행은 도입하지 않았다. 정책 확정 시 별도 검토한 삭제 절차가 필요하다.
이 설정은 영구 보관 승인을 의미하지 않는다. 사용자·문서 삭제 시 Django의 문서 삭제 신호가 관련 이벤트도
같은 삭제 트랜잭션에서 제거한다. FK는 SET_NULL이므로 이벤트의 직접 삭제 금지가 기존 부모 Admin 삭제를 막지 않는다.
사용자 이메일이나 FK는 이벤트에 없고 문서 삭제 후 개인정보 연결을 보존하지 않는다.

## 검증 및 확인하지 못한 문서

`python manage.py check`, `python manage.py makemigrations --check --dry-run`,
`python manage.py test`를 로컬·테스트 DB에서 수행한다. 전체 테스트에는 기존 앱의 회귀 테스트가 포함된다.
B10 테스트는 실제 파이프라인/답변 저장 연동, 오류·롤백·재시도, 시각 경계, 개인정보 차단,
운영 데이터 분류 제외, 관리자 권한, 부모 삭제, 일정한 쿼리 수와 읽기 전용 집계를 확인한다.
없는 Checklist/Schedule/검증 항목/만족도 기능을 테스트했다고 보고하지 않는다.

Notion 검색에서 「그려톤 전체 일정」, 「그려톤 백엔드 하네스」, 해당 프로젝트 PRD·기능명세서의 본문을
확인하지 못했다. 검색으로 확인한 일반 해커톤 주제 페이지에는 KPI·하네스가 없었다.
별도 개발 마감일은 만들지 않았다. 로컬 AGENTS.md·최상위 CONTRIBUTING.md·기존 백엔드 로드맵,
실제 API/AI 코드와 이번 사용자 지시의 우선순위·KPI 정의를 기준으로 구현했다.
